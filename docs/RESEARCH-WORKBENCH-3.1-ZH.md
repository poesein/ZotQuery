# ZotQuery 3.1.8 研究工作台

回答默认 Markdown 渲染，“Markdown 源码”用于编辑，返回“阅读”重新排版。复制和保存从源码读取，证据台账与正文保持分离。详见 [3.1.8 渲染说明](RELEASE-3.1.8-ZH.md)。

## 目标

3.1.8 将研究工作台改为以问题和大模型回答为中心的单列面板。视觉参考 ZotRadar 5.4.1 的蓝色标题栏、紧凑字体和连续内容区；保留原有 LNE/ZotSeek 来源追溯能力，但不强行复制其栏目。所有调用仍走 ZotQuery 自己的 API、数据库和扩展命名空间。

## 信息架构

- 顶部：研究问题与“大模型回答”主按钮。研究策略和可选人工会话折叠；不再要求先创建会话。
- 进度：一行显示问题、检索、核验、回答，以及候选列出、上下文阅读、审阅、直接事实计数。
- 主区默认“回答正文”，可编辑、复制、保存；另页“证据台账”保留原文链接、上下文、审阅和 FactRecord。内部台账文本在证据页折叠，不混入回答。
- 底部：折叠的运行日志、会话编号、索引状态和同步按钮。无左右固定栏，也无独立“检索与筛选”页面。
- 模型与输出：API、思考强度、模板及 BGE 配置均在 ZotQuery 设置中；工作台仅显示当前模型和模板摘要。
- Zotero 主工具栏：新增独立“研究工作台”图标，不再需要先进入右键菜单。

## 工作流与数据边界

1. “大模型回答”自动调用 `startOrchestratedResearch()` 检索并建立 PDF Coverage Gate 和持久化 LNE Survey，然后调用内置 API 模型的工具研究与写作阶段。这是针对问题使用已有索引，不是重建整个文库。
2. 相同问题和策略可以继续会话；问题或策略变化会建新会话，旧会话仍保留。折叠的“仅创建人工研究会话”供不调用输出模型的研究使用，不是必做前置步骤。笔记仍是导航，不因被命中而升级为原始证据。
3. 证据页通过 `positions()`、`positionContext()` 和 `reviewPosition()`维护门禁台账；读取上下文是审阅的前置条件。
4. DIRECT FactRecord 通过 `recordFact()`登记，继续遵守原有约束：PDF 来源、稳定 locator、肯定审阅、逐字短引以及值在短引中的有界出现。
5. “检查证据完整性”调用 `finalize()`。UI 不降低门禁，也不把空候选或部分分页写成完成。
6. 回答正文来自模型独立写作请求；内部台账文本从持久化 `researchResult()` 和 `ZotQueryOutputProfiles.render()`生成，始终独立，不覆盖回答。

## 内置 API 研究代理

3.1.8 的输出大模型不是一次性的“把现有 Markdown 润色一下”。插件将对外 MCP 使用的同一份 `zotquery_*` 工具定义和执行函数暴露给内置代理循环。支持 function/tool calling 的 API 模型可以在插件内依次执行健康检查、Query Contract、BGE/混合召回、LNE Survey、PDF 上下文读取、审阅、FactRecord、冲突处理、finalize 和模板渲染，效果等价于外部模型通过 MCP 编排，但不再依赖额外的 Codex、Claude Desktop 等 MCP 客户端。

内置 adapter 支持 Ollama、DeepSeek、OpenAI、Anthropic、Gemini、通义千问和自定义 OpenAI-compatible 服务。Provider、Base URL、模型、思考强度、工具轮数和超时在 ZotQuery 设置的“输出大模型与 Markdown 模板”中配置；“测试连接”发出一个极小的实际请求，而不是只检查 `/models`，测试不保存配置。思考强度提供“自动、关闭/最低、低、中、高”：自动不附加厂商专有参数，其余档位按 provider 转成对应参数；DeepSeek 普通 chat 模型仍由所选模型名决定推理模式。

### Markdown 模板输入

“按模板输出”实现为真正把一个 `.md` 文件全文交给输出模型，而不是只选择一个 Output Profile ID：

- 发布包与源码不附带 Markdown 输出模板。模板可选，未导入时可直接使用 API 生成证据约束的 Markdown 回答。
- ZotQuery 设置通过“导入 .md 模板”加载 Markdown 文件；保存的是文件路径，生成时重新读取当前内容，因此模板修改后无需重装插件。“清除模板选择”只清除路径，不删除原文件。
- 已选择的模板文件丢失或无法读取时，提示重新导入或清除选择；清除后即可无模板生成，不回退到内置模板。
- 模板全文置于 `<output-template>` 边界中，并明确标记为“不可信、仅用于格式”。模型必须遵守其章节、表格和字段，但模板不能修改工具 allowlist、索引范围、Coverage Gate 或密钥规则。
- 门禁通过后，编辑器显示模型按模板生成的正文；确定性 Output Profile 结果仍单独保留为审计数据，不再强行追加到模板正文后面。
- 生成结果的 HTML 注释记录模板名称和标题覆盖率，便于发现模型没有完整遵循模板的情况。

必须保持以下合同：

- 内置代理只允许调用研究 allowlist 中的工具；不能安装 profile、改写模型配置或绕过服务端验证。
- 模型看见的是它主动调用工具后返回的相关结果，不会一次上传整个 Zotero 库；但上下文工具返回的 PDF/Note 原文会发送给所选 API 服务。敏感文献应使用本机 Ollama，或确认远程服务的数据政策后再启用。
- API key 写入 Zotero Login Manager，不写入 `prefs.js`、普通偏好、日志、模板、报告或 XPI。界面和 `getConfig()` 只返回“是否已配置”，不返回密钥本身。
- `temperature` 以十进制字符串写入 Zotero 偏好；这是因为 Zotero 偏好不接受浮点类型。键名统一通过单点连接，避免空字段形成双点偏好键。
- HTTP 只允许 loopback/私有 IPv4；公网服务必须使用 HTTPS。
- 模型不能自行宣布研究完成。提前停止而核验未通过时，在剩余研究轮数内最多提示继续两次。研究结束后，另发一次无工具 API 请求，根据工具返回原文和持久化证据撰写回答，不使用早停的模型草稿。
- 只有 `status=ready_for_synthesis` 且 `synthesisAllowed=true` 才标为已核验回答。其他情况输出带明确未完成标记的阶段性回答，要求模型区分原文支持的信息与尚无法确认的部分，不能补造未闭合的精确事实。台账单独显示，不再替代回答。
- “保存回答 .md”只导出回答编辑框内容（含用户编辑），不附加审计台账、完整候选列表或机器 JSON。最终写作请求失败时显示错误，不回退为台账。

## BGE 向量模型与输出模型

这两类模型刻意分开：

- BGE/embedding 模型负责 PDF chunk 和 Note segment 的向量化与检索。工作台索引详情显示当前模型，完整模型合同和查询状态在 ZotQuery 设置中查看；“共享向量模型（BGE 等）”沿用原有向量模型管理和 embedding 服务接入。
- 输出大模型负责规划工具调用、阅读返回上下文并形成 Markdown。更换输出模型不会要求重建向量索引。
- 更换 embedding 模型、维度、归一化或预处理会形成新的向量空间，必须按原有模型合同验证或重建；不能仅因维度相同就复用缓存。

## 当前验收边界

- 已覆盖静态 XML、JavaScript 语法、UI 元素/事件契约、浮点偏好回归、可选 Markdown 模板、provider 消息转换、思考强度映射、系统凭据隔离、工具循环、阶段性回答与核验状态、台账独立显示/导出、版本一致性和既有离线回归。
- 该源码包没有自动安装到 Zotero，也没有宣称真实 Zotero 10 窗口视觉验收通过。
- 测试使用模拟 API 响应；尚未使用用户的真实 key 对每一家服务做在线调用。不同模型是否完整支持 function/tool calling 仍须用界面的真实请求测试和一个小型研究会话验证。
